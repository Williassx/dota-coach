# План развития Dota Coach

Статус: предложение для обсуждения. Это дорожная карта задач, а не утверждённый
технический план реализации. Код приложения пока отсутствует.

## Цель

Создать игру, в которой пользователь управляет командой из пяти игроков,
наблюдает симуляцию матча и влияет на результат приказами тренера.
Первый проверяемый результат — полноценный одиночный матч с повторным запуском.

## Предлагаемый подход

Начать с одиночного браузерного 2D-прототипа. Предлагаемый стек: TypeScript,
React и Vite для интерфейса, Canvas для карты, Vitest для симуляции,
Playwright для пользовательского сценария. Симуляция отделена от интерфейса
и использует фиксированные шаги времени и управляемый источник случайности.
Это предложение, а не уже выбранный стек.

Альтернативы: Godot для самостоятельной настольной игры; Unity для дальнейшего
перехода к более сложной графике. Браузерный вариант рекомендуется для быстрой
проверки карты, карточек и приказов из исходного эскиза.

## Границы первого прототипа

- Один локальный игрок-тренер против ИИ; две команды по пять виртуальных игроков.
- Упрощённая карта с тремя линиями и двумя базами.
- Перемещение, бой, возрождение и уничтожение базы как условие победы.
- Приказы: атаковать выбранную цель, отступить, фармить, сгруппироваться.
- Пауза, продолжение, изменение скорости и новый матч.
- Карта в центре; свои карточки снизу; соперники сверху; приказы и события справа.
- Карточки показывают роль, здоровье, уверенность и настрой.
- Сообщения объясняют принятие и исполнение приказов.

Карьера, полный набор героев и предметов, сетевой режим, 3D, реальные команды
и поддержка геймпада относятся к последующим этапам. Для прототипа используются
собственные условные изображения и небольшие локальные наборы данных.
Числа баланса, длительность матча и детальные правила фиксируются в спецификации.

## Порядок работы первой команды

1. Координатор (1) ведёт задачи и зависимости; владелец MVP (151) следит за объёмом.
2. Геймдизайнер (5) и архитектор (7) готовят спецификацию первого матча.
3. После согласования интерфейсов разработчик симуляции (41) и разработчик экрана
   (72) могут выполнять независимые задачи в разных файлах.
4. Разработчик командного ИИ (57) подключается после определения модели матча.
5. Разработчик панели приказов (76) подключается после определения интерфейса приказов.
6. Тестировщик (112/114) проверяет каждый результат; ревьюер (119) проверяет изменения.

Одновременно запускается только столько исполнителей, сколько допускает среда.
Роль — специализация: один исполнитель может последовательно выполнять разные роли.
Параллельная работа допускается при согласованных интерфейсах и непересекающихся файлах.

## Формат отдельной задачи

- Идентификатор и конкретный результат.
- Ведущая роль и проверяющая роль.
- Предшествующие задачи и входные интерфейсы.
- Разрешённые файлы и ограничения изменений.
- Проверяемые критерии приёмки и команды проверки.
- Фактический результат проверки и ссылка на изменения.

Статусы: запланировано → готово к выполнению → выполняется → проверяется → завершено.
Заблокированная задача фиксирует конкретную причину и необходимое действие.

## Условия перехода между этапами

Новый этап начинается после выполнения обязательных критериев предыдущего.
Для каждого крупного подсистемного этапа создаются отдельная спецификация и
подробный технический план с точными файлами, интерфейсами и тестами.
Сроки оцениваются после спецификации и первых задач; эта карта не обещает дату выпуска.

## Ближайший шаг

Согласовать браузерный 2D-прототип и границы первого матча. Затем подготовить
спецификацию этапов 1–6 для рассмотрения, после её согласования — технический план.
