# Локальная связь карточек и запроса ручного режима

**Дата UTC:** 2026-10-10. **Основа:** ffa3e84. Автономное выполнение разрешено пользователем.

## Цель и выбранный подход

Тренер выбирает карточку, а запрос сохраняет адресата при последующем выборе другой
карточки. Сначала реализуется локальная модель процесса, затем привязка экранов.
Она использует существующие DotaCoachRoster и DotaCoachInterventionRequests напрямую.

Варианты: отдельная связь панелей потребовала бы читать DTO двумя адаптерами;
расширение HUD сразу затронуло бы пакет и нативные проверки. Выбран один частный
координатор моделей, без копии правил и без изменения старого HUD/пакета.

## API и владение

DotaCoachInterventionSelection.create(adapterConfigured) создаёт по одному частному
Roster и Requests; только strict true означает настроенный переходник, а не онлайн.
Определения инертны. Методы replaceRoster(rows), selectPlayer(id), clearSelection(),
updateControl(frame), begin(), report(ticket,frame), expire(ticket), notSent(ticket),
view(), dispose(), isDisposed(). После dispose никакие данные не читаются.

view() возвращает {roster,manual,canRequest,message}. roster и manual — новые копии
view существующих моделей. manual.canRequest и общий canRequest дополнительно
учитывают availableForOrders выбранной карточки и последний принятый список.
Внутренние модели и ссылки не выдаются. MANUAL/ACK не означают право ввода.

## Выбор и доступность

replaceRoster вызывает существующую атомарную проверку списка (до пяти карточек).
Успех сохраняет выбор по ID, пока карточка selectable; удаление/foreign/unknown source/
unsupported снимает выбор. Dead карточку можно просматривать, но begin запрещён.
Отклонённый список сохраняет прежние карточки для просмотра, однако отключает
общий gate до следующего принятого списка. Это local fail-closed, не авторизация. Roster не содержит revision/epoch: порядок
обновлений обеспечивает источник. Структурно корректный старый список может быть
принят повторно; локальная модель не доказывает его актуальность.

Карточка выбирается через Roster. Requests выбирает тот же ID, если контрольный
снимок уже известен; иначе select(null), отображается отсутствие снимка, но выбор
карточки сохраняется. updateControl передаёт DTO только в Requests один раз и затем
вновь синхронизирует выбор. Снимок другого игрока не меняет выбранную карточку.
Неверный snapshot использует fail-closed правила Requests; cache не доказывает TTL.

begin проверяет объединённый gate, затем возвращает existing copied localintent.
Нет автоматического send. report/expire/notSent делегируются Requests: capturedactor,
sequence/epoch, неизвестный исход, поздний ACK и mode-observed не переопределяются.
notSent допустим только при доказанном отсутствии отправки вызывающей стороной.

## Атомарность и сообщения

Все мутации захватывают busy до чтения внешних DTO и увеличивают generation.
Вложенные мутации отвергаются без чтения их DTO. Busy view содержит пустые cards,
selectedId=null, manual.selected/request=null, canRequest=false и статус обновления.
После обработки внешних данных и перед завершением мутации проверяется generation/closed. Dispose побеждает
getter/reentry; завершение старого вызова не восстанавливает состояние.

Сообщение различает отсутствие списка/выбора/контрольного снимка, недоступную карточку,
отклонённый список и состояние existing запроса. Captured message не заменяется
именем вновь выбранной карточки. Одинаковые имена различаются ID.

## Проверки и ограничения

Node VM загружает три существующих определения и новый координатор. RED→GREEN сценарии выбор→snapshot,
snapshot→выбор, другой игрок/смена выбора/pendingactor, dead/foreign/unsupported/unknown,
неверный список/snapshot/highwater, mode/ACK/unknown/epoch/notSent, privatecopies,
busy DTO/view/getters/dispose/closed и отсутствие game API/send.
Пять критиков рассматривают дизайн и код. Это не связанный экран, транспорт,
серверное право, lease/ручное действие/возврат ИИ, реальная модель человека или Dota.

критик после подпроекта. Пять уже проведённых проверок — исторические факты.
