# C2-02-02: подтверждённый режим и состояние приказа

Пользователь поручил автономное продолжение отдела 2. Это новый небольшой модуль
Panorama: модель представления и панель двух приказов испытательной сцены.
Windows и общий контракт ещё недоступны; независимая подготовка не закрывает их.

## Выбранный подход

Только описать будущий экран — не проверяет ошибки состояния. Подключить GameEvents
сейчас — преждевременно фиксирует несогласованный протокол. Поэтому готовим UI
с явно передаваемым переходником send(intent, report), без игрового транспорта
по умолчанию. Модель и адаптер не выполняют приказы; сервер создателя 1 будет
проверять адресата, эпоху, цель, права и фактическое исполнение после контракта.
В этой задаче нет переключения MANUAL, маршрута кликов карты, голоса или ИИ.

## Частные входы представления

Это не общий wire-контракт и не имена событий Dota. Будущий переходник преобразует
авторитетные данные в данные UI, сопоставляет локальный ticket с сетевым request_id
и отдельным callback конкретного живого контроллера. Ticket не даёт полномочий
и не обещает уникальности между экземплярами/перезагрузками.

`DotaCoachOrders.create(transportReady)`:
setRecipient(snapshot), begin(action), report(ticket, update), expire(ticket),
notSent(ticket), view(), dispose(). Примитивные входы/выходы копируются.

Снимок содержит ровно id (устойчивый ключ карточки), playerName (до 64 символов),
mode (AI/MANUAL/INACTIVE), epoch и revision (неотрицательные безопасные целые),
side (own/opponent), availability (alive/dead/unsupported). Строки непустые;
id до 64 символов без пробельных краёв. null снимает выбранного адресата.
Хранятся последние снимки до десяти адресатов данного экземпляра UI. Для обновления
того же id нужны строго большая epoch либо большая revision в той же epoch;
старые снимки не откатывают состояние даже после A→B→A. Точный дубликат разрешает
повторный выбор уже известного адресата, но не обновляет его данные.

Одновременно отслеживается один незавершённый приказ для всего контроллера.
Смена выбранного адресата/null не снимает его блокировку: отдельно показывается
адресат самого приказа. A→unknown→B→A не разрешает повтор. Подходящий report
принимается и пока выбрана другая карточка. Только строго большая epoch того же
адресата прекращает отслеживание старого приказа с пояснением, что завершение
не подтверждено; это не отмена на сервере. Смена mode не подтверждается приказом.

До снимка режим неизвестен. begin допускает только move/attack и только своего
живого поддерживаемого адресата в подтверждённом AI, при наличии переходника
и отсутствии незавершённого запроса. Намерение содержит ticket, recipientId,
epoch, action; move/attack относятся к заранее заданным целям испытательной сцены,
не к произвольным координатам или entity index.

report получает ровно sequence (неотрицательное безопасное целое), stage
(accepted/executing/completed/rejected/cancelled) и reason (null или строка до
160 символов). Отказ/отмена требуют непустую причину. Нужны текущий ticket,
та же эпоха/адресат и возрастающая sequence. Ступень выполнения не регрессирует,
но промежуточный статус может быть пропущен. После терминального результата
дубликаты не меняют итог. Статус принятия не означает выполнение.
После копирования report повторно проверяются идентичность и актуальность запроса:
getter входа не может подтвердить новый запрос либо разыменовать уже снятый старый.

UI стадии: idle → pending → accepted/executing → completed/rejected/cancelled.
expire до первого ответа показывает unknown, не отменяет серверное действие
и не разрешает повтор; поздний подходящий report может прояснить результат.
Если send выбросил исключение до валидного ответа, результат unknown: транспорт
мог успеть передать намерение. Если report синхронно подтвердил accepted/completed
до исключения, полученный статус сохраняется. notSent допустим только до вызова send при отказе таймера;
показывает отдельный локальный сбой, не выдаёт его за серверный отказ.

## Панель и жизненный цикл

`DotaCoachOrderPanels.bind(root, send)` возвращает setRecipient/dispose/isDisposed.
Без send кнопки отключены; фикстуры никогда не подставляются автоматически.
Панель показывает выбранного адресата, адресата приказа, подтверждённый режим,
стадию и причину результата. Доступность команды для текущего выбранного адресата
выводится отдельной строкой; прежний отказ не скрывает текущую блокировку кнопок.
Кнопки: «К контрольной точке», «Атаковать тестовую цель». Метки text/html=false.
Обработчики проверяют текущее состояние и поколение отображения; старый callback
не становится новым кликом после A→B→A. Перед отправкой регистрируется локальное
ожидание и таймер первого ответа (2 секунды UI, не игровая длительность действия).
После любого валидного ответа этот таймер отменяется. accepted/executing остаются
незавершёнными до терминального ответа; их игровой срок задаст серверный контракт.

Ошибки отображения скрывают кнопки, закрывают контроллер и по возможности сообщают
недоступность. dispose освобождает события/таймеры, старые callbacks не действуют.
Явная XML демонстрация показывает синтетического адресата и имитированные ответы
переходника с явной подписью, без GameEvents/Players/Entities/Game/приказов Dota.
Повторная загрузка и уничтожение контекста освобождают старое demo; watcher
проверяет и IsValid, и isDisposed. Модули карточек не копируются и не меняются.

## Проверка и оставшиеся условия

Node VM исполняет реальные ES5 с моделью панелей/планировщика. Проверяются неизвестный
режим, AI/MANUAL/INACTIVE, свой/чужой/мёртвый/неподдерживаемый, ревизии/эпохи,
двойной клик, стадии/дубликаты/старые callbacks, тайм-аут и неопределённость отправки,
синхронный ответ, отказ таймера/рендеринга, dispose/reload. XML ссылки и панели
проверяются отдельно. Пять критиков рассматривают результат.

Приёмка «оба приказа меняют действие одного героя» не выполнена: нужен серверный
контракт, его переходник, C2-02-01, реальная сцена Dota и другой владелец.
Облачное демо не является подтверждением движения, атаки, MANUAL или персонального ИИ.

## Расширение для C2-02-03, 9 октября 2026 года

Модель и адаптер получили updateRecipient(snapshot) без смены выбора и
selectRecipient(id, playerName, allowIntents) без назначения режима. Boolean gate
ограничивает UI; существующие проверки AI/own/alive/переходника/busy сохраняются.
SetRecipient остаётся совместимым. Панель имеет одного владельца root до dispose.
Подробности — в [спецификации координатора](../03-control-input/design.md).
Это расширение исходных модулей, не копия и не закрытие серверной/нативной приёмки.
