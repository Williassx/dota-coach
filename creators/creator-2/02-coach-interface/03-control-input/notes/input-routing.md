# Подключение координатора

[Подпункт](../README.md) · [Дизайн](../design.md) · [Отчёт](../reports/cloud-routing.md)

## Порядок и владение

Использовать единственные исходники из C2-02-01 и C2-02-02: модель roster,
адаптер roster, модель orders, адаптер orders, затем input_routing.js.
Каждый скрипт загружается один раз. Выбранные root должны содержать необходимые
панели своих адаптеров и оставаться живыми. Разметка этих подпунктов пока включает
отдельные demo; запуск общего HUD потребует отдельной согласованной интеграции.
Координатор не подключается поверх уже запущенных demo и не загружает XML сам.

Живые адаптеры владеют root исключительно. Повторный bind бросает исключение
до изменения обработчиков. Dispose освобождает владение. Bootstrap будущего HUD
должен хранить и освобождать старый координатор перед повторной привязкой.

## Потоки данных

replaceRoster(rows) получает локальные данные карточек из спецификации C2-02-01.
Успешный replace/select/clear сообщает отдельную копию выбранного view либо null.
availableForOrders отличается от selectable: мёртвого можно рассматривать, но
нельзя отправить ему намерение. Ошибка callback закрывает roster; после callback
повторно проверяется, не закрыл ли потребитель контроллер.

updateControl(snapshot) использует прежние поля и версионирование C2-02-02.
Фоновый снимок не меняет выбор и gate карточки. Без снимка имя выбранного игрока
известно из roster, режим неизвестен. Имя выбранного берётся из карточки; имя
адресата отправленного запроса — из контрольного снимка. id связывает данные,
имя не служит авторизацией. Некорректный вход сохраняет последние данные.

send(intent, report) необязателен. Без функции кнопки отключены. Вызов переходника
требует явного клика по доступной кнопке; он не возникает при выборе карточки
или обновлении режима. Намерения move/attack ещё относятся к фиксированным целям
испытательной сцены. Авторитетные права, реальные цели, корреляция и восстановление
после reload остаются серверу/общему контракту.

Один unresolved запрос сохраняется при удалении, снятии или смене выбранного
игрока; unknown не разрешает повтор. Только новая epoch исходного адресата снимает
отслеживание, не объявляя выполнение/отмену серверного действия.

Контрольный cache хранит последний известный снимок даже после remove/null.
Повторное появление того же stable id использует его сохранённый режим; это не
свежее подтверждение. В пределах экземпляра id не назначается другому игроку.
Новый матч требует нового контроллера, смена поколения — корректной epoch от
производителя. Переходник/сервер должны синхронизировать данные и проверять текущие
права до исполнения. Срок свежести и восстановление после reload ещё не согласованы.

## Закрытие

Watch каждые 0.25 секунды проверяет оба root и закрытие дочерних адаптеров.
Непосредственно перед send и поздним report проверяются те же условия. Поэтому
уничтожение roster между тиками не позволяет вызвать переходник или применить ответ.
Отказ регистрации watcher освобождает уже привязанные панели. При dispose
отменяются watcher, таймер первого ответа и обработчики; старые callbacks не действуют.

## Нативная приёмка

Нужно собрать общий HUD без demo, подтвердить resource paths/компиляцию,
hittest и распространение кликов, отделение карты от панели, живые snapshot/ответы,
смену героя и восстановление состояния после reload в настоящей Dota.
API Schedule/CancelScheduled и методы панелей сверены с ранее закреплёнными
[декларациями ModDota](https://github.com/ModDota/TypeScriptDeclarations/tree/df7722b560d5c616f7b2f6be42480aa5053baec8).
Это community reference; фактическая версия Windows не подтверждена.
