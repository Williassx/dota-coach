# Локальная история отображаемых приказов

Основание: справа на эскизе находится связь/журнал; DC-026 требует адресата,
принятие, отмену и результат. Ведущий — основной исполнитель отдела 2.

Первый независимый шаг — pure модель, принимающая только существующий
`DotaCoachOrders.view()` из C2-02-02. Новый серверный контракт не создаётся.
Один экземпляр истории принадлежит одному экземпляру Orders; после смены сцены
оба пересоздаются. Вызов `record(view)` явный: polling/подписки/transport не добавляются.

Сохраняются изменения текущего ticket/stage/reason и первоначальные адресат/действие.
Выбор другой карточки, режим и canIssue не создают события и не меняют старый адресат.
Первый снимок может быть completed: недостающие стадии не выдумываются. Новый ticket
строго больше прежних; уменьшение/повтор после прекращения отслеживания отклоняются.
Стадии одного ticket следуют допустимым переходам существующей модели; завершённый
результат не переписывается. Потеря текущего ticket отмечается `tracking-ended`,
а не отменой/исполнением; смена ticket без снимка idle также явно закрывает старое
отслеживание. Это наблюдения UI, не полный серверный журнал или причинное объяснение.

История ограничена 64 событиями; старые удаляются с явным счётчиком droppedEvents.
Повторы и invalid inputs ничего не вытесняют. Возвращаемые данные копируются.
Вход — exact own data descriptors, без getters; busy guard предшествует Proxy traps,
reentry отклоняется, dispose во время чтения закрывает и очищает историю.
Ограниченные plain строки готовятся для будущих Label(html=false); HTML не исполняется.

Для каждой записи evidence=presentation_snapshot, nativeConfirmed=false. Тексты
различают принятие и сообщение о результате; completed не доказывает эффект в Dota.
Нет ASR, HUD/bundle расширения, реальных временных меток или server identity/sequence.
Panorama-панель, связь с общим HUD и native приёмка остаются следующими шагами.
