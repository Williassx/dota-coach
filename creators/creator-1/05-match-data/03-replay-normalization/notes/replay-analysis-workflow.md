# Повторяемый разбор реплея после двух матчей

[Подпункт](../README.md) · [Импортёр](dem-import-usage.md) · [Первый процесс](../reports/01-match-9042986015/efficient-analysis.md) · [Проверка на втором матче](../reports/05-match-9045392898/README.md).

15 октября 2026. Это улучшение проектной процедуры. Веса модели Codex, глобальная память и игровые политики не изменяются.

1. Один запрос метаданных: match/account/hero/replay URL, исходные байты и SHA. Один download/decode по magic; Zstandard не пробовать как BZip2 из-за расширения. Подготовленные JAR/JDK повторно не устанавливать.
2. Новый класс требует измеренной схемы. Сохранить fail-closed diagnostic, независимо проверить descriptors, добавить только точные ключи с отдельным DEM provenance. Без auto-allow, wildcard и замены старого основания новым.
3. Перед длинным матчем выбрать явный ограниченный бюджет индекса. На 60:20 реально получено 11872 entries; default10000 дал отказ. Локальный лимит30000 прошёл при прежних byte/heap/timeout caps. Не увеличивать лимиты вслепую и не публиковать failed stage. Новый профиль проверять регрессией прежнего матча и повторяемостью нового.
4. Один root управляет Dota. До запуска проверить отсутствие чужого клиента; сохранить свой PID и точный StartTime UTC. Слушающий порт не означает готовность VCon: нужны marker и ответ команды. Внутренние кавычки обязательны: `playdemo "D:/path/file.dem"`, иначе console может разобрать путь как D.dem. После перехода между replay и меню сначала проверить готовность нового состояния.
5. Сначала два свежих игровых PNG: верный replay/POV, продвижение HUD, разные изображения. Потом обычные и событийные окна по actual DEM clock. Не переносить старый slot, offset или формулу времени. Использовать game-only PNG; не повторять известные неработающие GDI/Sky graphics пути. Window API нужен для активации актуального окна.
6. Каждый кадр получает before/after cursor, PNG hash и ближайшую предыдущую real row с gap. Без интерполяции. HUD clock читать отдельно: 38/42 floor совпали, четыре +1s сохранены; два из них имеют exact row. Причина неизвестна. Записанная игровая пауза отличается от паузы просмотрщика. Фиксировать текущий Steam build и native engine version, не ссылаться автоматически на прошлую установку.
7. PlayerView не гарантирует selected unit == target hero. Проверять панель и контекст; явные Techies/«ВОИН ШТОРМА» и сводки смерти другого игрока исключить. Не переносить начальный player-view caption на все кадры; непрочитанное имя хранить как unknown. На втором матче 36 eligible panels согласовались в пределах одной единицы HUD, шесть исключены; все исключения сохранены.
8. Аналитик API, самостоятельный аудит процесса/descriptor при новой схеме, root visual, затем один итоговый C2 review. Давать компактный пакет эпизода с hash/tick/source pointers. Сначала контактные листы, затем нужные оригиналы. Семь листов/42 кадра — измеренный объём; это не процент экономии токенов.
9. Наблюдения, гипотезы и неизвестное разделять. Около70–98% маны перед пятью смертями и около15% перед последней — ресурсные точки, а не оценка причин. Покупка, результат команды и имя события не являются action labels или характером. Оба просмотренных матча относятся к development; untouched test нужен отдельно.
10. Восстановить временные cvars с readback, проверить свой PID quit→gone и Steam retained. Выполнить targeted tests, JSON/links/hashes, итоговый обзор и одну usage-запись с tokens/cost=null. Общий каталог повторять при изменении кода или неразрешённом сбое. В Git публиковать компактные доказательства, а не raw DEM/JSONL/PNG/toolchain.

Отдельные будущие задачи: bounded schema audit до полного parse; создание actor-action labels, допустимых player observations и heldout split перед обучением игровой политики. Их нельзя незаметно добавлять в задачу разбора нового матча.
