# Телеметрия 9042986015: что действительно извлечено

14 октября 2026. [Версии и доказательства](telemetry-spike.json) · [Исследовательский протокол](../../experiments/01-local-dem-telemetry/README.md).

Clarity5.0.1/protobuf7.1 прочитал исходный `.dem` до tick68100. Первый проход занял10,607с; расширенный сбор ресурсов/контроля/событий —18,218с. Это измерения отдельных локальных запусков, не время всего исследования и не измеренная экономия токенов.

[Независимый C2 обзор](technical-review.md) сверил реальные output/CSV, хэши и ограничения. Ошибка в описании первой записи времени исправлена; незакрытых P1/P2 замечаний нет. Это приёмка исследовательского извлечения, без принятия production importer или строгой native calibration.

Получены34051 real tick-end записи. Для32178 из них подтверждена привязка Dendi к герою;1873 не имели подходящей привязки и не попали в CSV игрока. Дополнительно обработаны34050 synthetic tick callbacks, но как реальные состояния они не сохранялись. Real packets обычно разделены двумя game ticks: это примерно15Hz, а не измерение реакции человека с точностью30Hz.

CSV содержит также pre/postgame состояния и raw game_state. Они не должны автоматически превращаться в игровые обучающие эпизоды. Временные метки вне активной игры и неизвестные поля сохраняются отдельно.

Игровое время рассчитано по server tick, накопленным pause ticks и ненулевому start time. Устаревшее `m_fGameTime` отсутствует. Разность server tick−demo tick464 наблюдалась34050раз; только первая запись demo_tick0/server_tick463 имела463. Последняя запись68100/68564 имела464. Поэтому фиксированный сдвиг demo tick не используется вместо реального сообщения времени. Пока start не известен, время неизвестно. Это offline spectator telemetry, а не доказательство того, что игрок видел всё записанное.

Два инструментированных прохода дали **побайтно одинаковые samples.jsonl**; добавление combat/schema observers не изменило снимки состояний. Это повторяемость одного парсера, не независимая реализация декодирования.

## Обнаруженный риск декодирования ID

Actual field schema показала `m_iPlayerID:PlayerID_t`, декодер `IntVarUnsignedDecoder`. В pinned factory PlayerID_t отдельно не зарегистрирован и попадает в unsigned fallback. Это объясняет, почему поле требует отдельной проверки; wire bytes/предполагаемое signed значение не исследованы. Деление14на2 не применялось. Сведения о типе/декодере не доказывают причину несовпадения ID. Атрибуция строится по SteamID и полному выбранному handle, а не по этому полю.

## Локальные результаты и следующий объём

CSV: `build/dota_coach/replay-9042986015/telemetry-spike/run-3/storm-telemetry.csv`. Полные replicated snapshots, target combat events и modifier table entries лежат рядом; в Git публикуются только исследовательские выводы/хэши. Java source временный, один локальный экземпляр в библиотеке создателя1; игра, schema общих контрактов и обученная модель не менялись.

Следующий сохраняемый импортёр требует: проверяемого schema/version gate, обобщённого actor binding без фиксированного slot/handle, точной native калибровки, подтверждённых coordinate/control mappings, формата компактных пакетов и отказов. До этой спецификации текущий probe остаётся экспериментом. Пользовательские решения, понятия допустимого знания и критерий сходства не подменяются статистикой одного матча.
