## Предварительная интерпретация

В этом матче Storm совмещает линию, нейтральный фарм и участие в боях. Первый результативный боевой отрезок заканчивается смертью после падения HP и маны. Позднее видны иные ограничения — привязка и оглушение при ещё достаточных ресурсах. Поэтому будущая модель должна учитывать **ресурс для выхода и доступность выхода под контролем отдельно**. Нельзя свести поведение к одному коэффициенту агрессии.

В нескольких сценах рядом Io. Поддержка союзника — часть контекста: наблюдаемый запас/восстановление ресурсов нельзя автоматически считать самостоятельной особенностью Dendi. Выбранные сцены не доказывают ни дружелюбие, ни коммуникацию, ни мораль. Командное поражение и небольшой урон по зданиям также не доказывают личную причину поражения.

API сообщает neutral_kills 164 и lane_kills 166. Их сумма 330 не совпадает с 343 last hits: это разные категории, их нельзя превращать в исчерпывающий процент лесного фарма. Позиционные heatmap не дают непрерывной траектории. Сводные KDA/GPM сами по себе не оценивают качество решений.

## Что сохранять для модели игрока

Для каждого решения нужен контекст: роль/герой/уровень, HP/mana, восстановление, cooldowns, контроль, видимые противники и союзники, командная экономика, цель и результат. Отдельно сохранять признаки, оценённую политику и игровые черты персонажа. Для неизвестных полей — `null`, а не реконструкция по догадке.

Этот матч — исследовательский пример. Из него можно извлекать кандидаты признаков: выбор линия↔нейтралы, ресурс перед боем/выходом, реакция на контроль, предметные этапы, участие при поддержке Io. Устойчивые параметры требуют повторения на других матчах и сравнения при сопоставимых условиях. Обученная модель и её сходство с Dendi пока не подтверждены. Уже просмотренный матч не оставляется нетронутым финальным тестом.

Имитация игрока и улучшение игры тренером — разные задачи. Не заменять реальные решения «идеальным ботом» и не записывать результат исправления как поведение Dendi. Тренерские рекомендации из первого матча можно формулировать как вопросы: сохранялся ли ресурс на выход, учитывались ли доступные enemy disables, зачем выбран момент входа? Ответ требует полной локальной цепочки событий и допустимых знаний игрока.

## Ограничения и следующий технический шаг

Root единолично управлял Dota. Native help показывал PlayerView mode 3 и Dire fog mode 3, а PNG — POV `v o i d`; это не полная проверка исторического доступного знания. Физический ввод не контролировался; качество обновления захвата проверялось по HUD и хэшам.

Для быстрого масштабирования нужен машинный разбор `.dem` с локальной временной шкалой состояний и метками происхождения; API здесь не содержит всех нужных полей. Извлечение этой телеметрии и обучающий runtime не реализованы данным исследованием. Следующий отдельный технический объём — проверить извлечение таких полей на нескольких известных кадрах, затем давать анализаторам короткие пакеты событий. [Рабочий порядок](efficient-analysis.md) описывает кеш, контроль захвата, обычные контрольные отрезки и измерение расхода без выдуманных процентов экономии.

Checklist проекта не повышен: исследование реального матча не означает готовность персональной модели или всей игры.
