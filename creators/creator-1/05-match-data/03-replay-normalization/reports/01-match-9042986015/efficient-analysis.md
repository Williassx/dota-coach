# Как ускорить разбор, сохраняя доказательства

[Матч](README.md). Запрос пользователя от 14 октября 2026: меньше токенов и времени, высокий уровень анализа. Это рабочая рекомендация и порядок текущего исследования, не новый игровой модуль и не измеренная экономия.

## Где расходуется время

В этом запуске основная задержка — получение проверенного изображения, а не игровые выводы. Window capture не работал; обычный клиент не предоставлял команды экспорта. Tools предоставил `png_screenshot`, но `cl_playback_screenshots=false` блокировал экспорт. После включения получены реальные PNG. Один разрешённый desktop probe не доказал игровую сцену и не публикуется.

Первый обзор сохранил 88 одинаковых кадров итогового экрана. Второй/третий обзор остановились после трёх одинаковых изображений. Наличие `Currently playing` и изменение demo ticks недостаточны: изображение может не обновляться. Проверяем одновременно файл реплея, героя/режим камеры, читаемые часы HUD и новые кадры. Причина остановки визуального обновления пока не изолирована; после повторной активации окна появился актуальный кадр 15:27. Physical input не контролируется.

## Порядок одного матча

1. **Один приём данных.** Проверить match id, игрока, героя, патч и источник. Сохранить исходный реплей, API, размеры и SHA256 локально. Читать формат по magic bytes: `.bz2` в этом случае содержал Zstandard. Повторные запуски используют проверенные файлы; смена хеша/версии источника требует пересчёта.
2. **Расчёты без языковой модели.** Один проход создаёт компактные факты и индекс событий: покупки, убийства, смерти, драки, ресурсы. Все числа имеют указатель в источнике. API и demo tick не смешиваются; соответствие проверяется по фактическим часам HUD. Недоступная траектория/ввод не восстанавливаются из heatmap.
3. **Сначала проверка захвата.** До длинного запуска получить два свежих игровых кадра с продвижением часов и верным POV. Три одинаковых кадра останавливают автоматическую запись для проверки: это сигнал проблемы, не доказательство её причины. Постматчевые меню не входят в игровое покрытие. При смене клиента/сборки проверка повторяется.
4. **Обзор и подробные эпизоды.** Обзор нужен для общей структуры; короткие окна до/во время/после события — для решения и результата. Добавить обычные отрезки линии, леса, ротации и восстановления, в том числе отрезки вне автоматического списка событий. Грубая обзорная частота не позволяет судить о микроконтроле.
5. **Два независимых результата.** Аналитик ранней игры и аналитик средней/поздней игры получают разные эпизоды и только нужные факты/кадры. Root единолично управляет Dota и сопоставляет выводы. Один итоговый reviewer проверяет завершённый отчёт. 175 специализаций — каталог применимых обязанностей, не 175 одновременных процессов.
6. **Компактный пакет эпизода.** Match/actor/source hash; фактические часы каждого кадра; API pointers; наблюдаемое действие; доступная информация; возможные альтернативы; результат; неизвестные факторы. Полный raw log не переносится в каждый запрос. Изображения — сначала контактный лист, затем оригинал только там, где деталь необходима.
7. **Один накопительный отчёт.** `observed`, `hypothesis`, `unknown` разделены. Новые матчи добавляют свидетельства и проверяют предыдущие гипотезы. Один матч не подтверждает мораль, дружелюбие, характер или устойчивый персональный стиль; результат команды не является оценкой решений отдельного игрока.
8. **Проверка сходства отдельно.** При десяти матчах заранее разделить данные для исследования, настройки и отложенной оценки с учётом роли/героя/патча. Распределение зависит от покрытия данных; десять матчей не гарантируют достаточность. Уже просмотренный 9042986015 не является нетронутым тестом. Модель должна проверяться против реальных отложенных действий и базового бота.

## Ограничение повторной диагностики

Для уже известной ошибки сначала читать проектный урок. Не повторять команду без изменения условий. После двух неудачных одинаковых попыток остановить этот путь; разрешается новый путь с конкретной проверяемой гипотезой. До масштабной записи обязателен короткий проверенный pilot. Raw replay/desktop/account logs остаются ignored local; в Git — результаты, источник и границы доказательства.

## Как проверить экономию и качество

По каждому матчу учитывать отдельно подготовку клиента, загрузку/парсинг, захват, анализ и проверку; число просмотренных эпизодов/кадров, повторные действия, долю покрытия, противоречия API↔HUD и неподтверждённые выводы. Если доступны usage — input/output/cached tokens и стоимость, иначе `null`. Время одинакового этапа сравнивать только при сопоставимых условиях. Сегодня общего счётчика токенов нет: проценты экономии не объявляются.

Критерий качества: каждое содержательное утверждение имеет источник и время; неоднозначность сохранена; выборка содержит событийные и обычные отрезки; независимая проверка не обнаружила подмены наблюдения предположением. Быстрее не означает достаточность данных для оцифровки игрока.
