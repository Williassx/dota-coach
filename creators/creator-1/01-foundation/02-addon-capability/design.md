# C1-01-02: минимальная серверная сцена и обработчик подтверждения

Пользователь подтвердил использование компьютера для задач создания кастомки.
Задача — минимальная серверная часть: аддон с одним героем, проверка серверного
приказа на движение/атаку, лог и наблюдение подтверждают идентичность героя.
UI (Panorama) — предмет параллельного C2-01-02; общий контракт приказов — C1-01-03.

## Подход

Готовится собственная папка аддона в этом подпункте (`src/`), единственный
серверный скрипт `scripts/vscripts/addon_game_mode.lua`. Плюс минимальный
`addoninfo.txt` и карта: используется фактическая карта шаблона `template_map`
(копия, как у создателя 2), потому что собственная сборка карты ранее давала
ERROR_FILEOPEN базовых ресурсов. Изменение установки игры выполняется только
отдельной опубликованной командой копирования, после записи плана.

## Поведение

1. При активации аддона Lua печатает однозначный лог-префикс `D1C102 …` —
   это подтверждение работы серверного скрипта, не дружественный интерфейс.
2. В первый ход (`DOTA_GAMERULES_STATE_GAME_IN_PROGRESS`) скрипт создаёт одного
   штатного героя на зоне спавна, отдаёт ему приказ движения к видимой цели
   и печатает наблюдение о созданной сущности — точный набор API
   (CreateUnitByName/ExecuteOrderFromTable и имена героя) закрепляется в
   implementation-plan.md по фактическому Lua-файлу, а не выдумывается заранее.
3. Наблюдение в логе подтверждает идентичность: индекс сущности, имя героя и
   владельца; это соответствует приёмке «лог и наблюдение подтверждают
   идентичность героя».

## Границы

- Ретрансляция UI-событий и общий контракт находятся в паре с C1-01-03/C2-01-02;
  здесь только сервер и факты логов. Это проверка механизмов: полный цикл
  ИИ/мышь/возврат принимается позже в отдельные подпункты.
- Запуск dota2.exe сам по себе не считается успехом; успех = подтверждённое
  выполнение приказов по логам/наблюдению.
- Выполняемые действия цели — только прямое движение и простая атака;
  их идентификаторы приказов см. в implementation-plan.md.
