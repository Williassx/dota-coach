# Выбор агентов и экономия контекста

[Настройки](agent-policy.json) · [Учёт](agent-usage.jsonl).

## Решение пользователя

Обычные ответы, обсуждение и планирование ведёт основной исполнитель самостоятельно.
Критик подключается только после окончания подпроекта: заранее определённого результата
с критериями приёмки и связанными изменениями. Ответ на вопрос и каждый подпункт плана
не являются отдельным поводом для проверки. Дополнительных критиков подключают только
к конкретному нерешённому замечанию либо по прямому запросу пользователя.
Ранее выполненные проверки пяти критиков остаются историческими фактами.

## Роль 173 — диспетчер агентов

Перед задачей основной исполнитель выполняет эту роль: определяет результат, область
файлов, зависимости и необходимость помощи. По умолчанию подагентов нет. Один
исполнитель допускается для самостоятельного результата с отдельными файлами,
если передача задачи действительно сокращает работу основного исполнителя.
Не запускайте отдельного диспетчера ради решения, нужен ли диспетчер.
После завершения подпроекта одна итоговая критическая проверка заменяет регулярные
параллельные проверки на каждом шаге. Второго человеческого владельца она не заменяет.

Краткое назначение содержит только задачу, выбранные файлы, ограничения и критерий.
Передавайте его без полной истории (`fork_turns=none`); существующего агента используйте
повторно. Модель выбирайте среди реально доступных и разрешённых для этой задачи.
Репозиторий не переключает модель текущего чата и не меняет тарификацию провайдера.

## Роль 174 — учёт расхода

Основной исполнитель один раз на завершённую задачу добавляет запись в agent-usage.jsonl.
Если платформа предоставила usage, сохраняйте числовые input/output/cached tokens,
стоимость с валютой и источник показателей. Если данных нет — null и причину.
Не выводите стоимость из длины текста, числа тестов или количества агентов.
Отдельная постоянная модель для сбора учёта не запускается: она сама увеличила бы расход.
При доступном экспорте usage можно заполнить данные позднее с указанием источника.

## Роль 175 — оптимизация контекста

Читает учёт и решения диспетчера при следующем планировании; убирает повторное
исследование, дублирующие задания и ненужную полную историю. Это роль исполнителя,
а не постоянный фоновый процесс. Не создавайте отдельного агента для каждого отчёта.

- Навык читается один раз на применение; затем используйте сохранённое понимание.
- Ищите через rg, читайте нужные диапазоны и изменения вместо целых больших документов.
- Сохраняйте длинные тестовые логи локально; выводите итог, при ошибке — нужный фрагмент.
- После изменения выполняйте целевые проверки; обязательные проверки перед публикацией
  сохраняются. Повтор полной регрессии нужен при новом коде или неразрешённой ошибке.
- Обновляйте единственный отчёт, журнал и индексы вместо нескольких одинаковых пересказов.
- Ограничения длины brief/вывода в JSON мягкие: важные условия и доказательства не обрезайте.

Точный расход токенов и денежная экономия не объявляются измеренными без usage.
Числовой лимит в настройках остаётся null: без счётчика его нельзя достоверно обеспечить.
JSON — настройки рабочего порядка, которые исполняет агент по AGENTS.md; это не новый
сервер управления моделями и не установка лимитов в аккаунте.
