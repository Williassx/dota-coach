## Решение пользователя

Последнее поручение пользователя, 12 октября 2026: использовать все 175 ролей по
правилам репозитория, продолжать самостоятельно и учиться на действиях. Предыдущий
порядок одного помощника расширен до полезных групп в пределах доступных слотов;
запрос не означает одновременный запуск 175 процессов или добавление игровых механик.
[Реестр подключения](../creator-2/01-foundation/01-workspace-audit/notes/agent-activation-2026-10-12.md)
содержит каждый номер, этап, ведущего владельца, статус, условие и критерий результата.
Обычные ответы и обсуждение ведёт основной исполнитель самостоятельно. Для планирования
он использует роли каталога; отдельный агент нужен для самостоятельного результата.
Критик подключается только после окончания подпроекта: заранее определённого результата
с критериями приёмки и связанными изменениями. Ответ на вопрос и каждый подпункт плана
не являются отдельным поводом для проверки. Дополнительных критиков подключают только
к конкретному нерешённому замечанию либо по прямому запросу пользователя.
Ранее выполненные проверки пяти критиков остаются историческими фактами.

## Роль 173 — диспетчер агентов

Перед задачей основной исполнитель выполняет эту роль: определяет результат, область
файлов, зависимости и необходимость помощи. Просматривает роли соответствующего этапа,
назначает отдельные результаты и фиксирует неактивированные зависимости.
Отдельный исполнитель допускается для самостоятельного результата с отдельными файлами,
если передача задачи имеет понятную пользу. Повторное разрешение пользователя на такие
группы не требуется; разрешения среды и явные ограничения конкретной задачи сохраняются.
Не запускайте отдельного диспетчера ради решения, нужен ли диспетчер.
После завершения подпроекта одна итоговая критическая проверка заменяет регулярные
параллельные проверки на каждом шаге. Второго человеческого владельца она не заменяет.

## Группы этапов и предел среды

Лимит текущей среды — четыре процесса всего: основной и максимум три помощника.
Диспетчер выбирает минимум полезных независимых результатов и размещает их в свободных
слотах. Не заполняйте слоты пустыми заданиями ради численности. После результата слот
используется повторно; зависимые части выполняются после входных результатов.
При меньшем лимите используйте фактический; JSON не повышает лимит инструмента.

Перед группой зафиксируйте роли, файлы, интерфейсы, входы, проверки и критерии.
Координатор остаётся одним из двух равноправных создателей; сервер/ИИ/данные принадлежат
создателю 1, UI/карта/мышь/голос — создателю 2. Общий файл имеет одного автора.
Консультации смежных ролей не создают вторую реализацию. Отдельный ИИ-критик не считается
проверкой другим человеческим владельцем. Назначения с `planned/blocked` переходят
к исполнению после зависимости; независимый аудит возможен до нативной сцены.
Полное покрытие реестра не означает, что все роли уже дали фактический результат.

Краткое назначение содержит только задачу, выбранные файлы, ограничения и критерий.
Передавайте его без полной истории (`fork_turns=none`); существующего агента используйте
повторно. Модель выбирайте среди реально доступных и разрешённых для этой задачи.
Репозиторий не переключает модель текущего чата и не меняет тарификацию провайдера.

## Роль 174 — учёт расхода

Основной исполнитель один раз на завершённую задачу добавляет запись в agent-usage.jsonl.
Если платформа предоставила usage, сохраняйте числовые input/output/cached tokens,
стоимость с валютой и источник показателей. Если данных нет — null и причину.
Не выводите стоимость из длины текста, числа тестов или количества агентов.
Отдельная постоянная модель для сбора учёта не запускается: она сама увеличила бы расход.
При доступном экспорте usage можно заполнить данные позднее с указанием источника.

## Роль 175 — оптимизация контекста

Читает учёт и решения диспетчера при следующем планировании; убирает повторное
исследование, дублирующие задания и ненужную полную историю. Это роль исполнителя,
а не постоянный фоновый процесс. Не создавайте отдельного агента для каждого отчёта.

После значимого успеха и сбоя фиксируйте короткий проектный урок: что делали,
наблюдаемый факт/команда и доказательство, причина, принятый способ и следующая проверка.
Перед похожим действием найдите соответствующий урок; повтор неудачного шага допускается
только с новым основанием или изменением условий. Урок и факт живут в библиотеке автора
и журнале действий; общие правила меняются одним автором, когда применимы к обоим.
Это улучшение рабочего порядка; веса модели и глобальная память Codex не изменяются.

- Навык читается один раз на применение; затем используйте сохранённое понимание.
- Ищите через rg, читайте нужные диапазоны и изменения вместо целых больших документов.
- Сохраняйте длинные тестовые логи локально; выводите итог, при ошибке — нужный фрагмент.
- После изменения выполняйте целевые проверки; обязательные проверки перед публикацией
  сохраняются. Повтор полной регрессии нужен при новом коде или неразрешённой ошибке.
- Для source-регрессии используйте [единый каталог и исполнитель](../creator-2/11-integration/03-end-to-end/README.md).
  Полный прогон: `python3 creators/creator-2/11-integration/03-end-to-end/tools/run_source_checks.py`.
  `--suite` — целевой прогон со статусом partial, он не заменяет обязательную полную
  регрессию. Полные логи сохраняются отдельно; в контекст выводите краткий итог и ошибки.
- Обновляйте единственный отчёт, журнал и индексы вместо нескольких одинаковых пересказов.
- Ограничения длины brief/вывода в JSON мягкие: важные условия и доказательства не обрезайте.

Точный расход токенов и денежная экономия не объявляются измеренными без usage.
Числовой лимит в настройках остаётся null: без счётчика его нельзя достоверно обеспечить.
JSON — настройки рабочего порядка, которые исполняет агент по AGENTS.md; это не новый
сервер управления моделями и не установка лимитов в аккаунте.
