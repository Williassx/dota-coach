# Устройство рабочей библиотеки

Основание: пользователь поручил создать в основном репозитории папки двух
равноправных создателей, разделы и подпункты, вести работу сначала в них и начать
первый подпункт создателя 1. Это правила организации; спецификации игровых функций
рассматриваются отдельно по мере проверки Workshop Tools.

## Разделение работы

- Создатель 1: серверные скрипты, наблюдения, ИИ, данные, арбитр приказов и состояния.
- Создатель 2: Panorama, карта/камера, ввод мышью, голос и отображение состояний.
- Ни один не является начальником другого. Каждый проверяет изменения второго;
  после необходимых проверок объединить изменения вправе любой.
- Права в GitHub настраиваются отдельно от папок. Папки распределяют ответственность,
  а не предоставляют или отнимают доступ к репозиторию.

## С чего начинать каждую задачу

1. Прочитать корневой AGENTS.md, AGENTS.md и PLAN.md своего создателя.
2. Открыть README нужного раздела и подпункта; проверить зависимости и приёмку.
3. Объявить ID задачи и разрешённые файлы. Исследования и новые исходники сразу
   размещать в этом подпункте, а не в случайной папке корня.
4. Перед реализацией функции сохранить здесь её `design.md` и, после рассмотрения,
   `implementation-plan.md` с точными API, файлами и командами проверки.
5. Реализовать только согласованный объём, проверить, записать фактический результат
   в `reports/` и обновить статус в README подпункта.
6. Передать изменение второму создателю. Для параллельных задач выбрать разные файлы.

Список из 72 подпунктов является организационным планом проекта, а не готовыми
техническими планами всех функций. До проверки установки в них не выдумываются
API, пути сборки и команды тестов Dota.

## Имена и вложенные папки

```text
creators/
  creator-1/ или creator-2/
    PLAN.md
    AGENTS.md
    NN-section/
      README.md
      NN-subsection/
        README.md
        design.md                 # при проектировании конкретной функции
        implementation-plan.md    # после рассмотрения её design.md
        src/                      # при появлении исходников
        tests/                    # при появлении проверок
        fixtures/                 # малые примеры без секретов
        tools/                    # помощники именно данного подпункта
        notes/                    # исследования и решения
        reports/                  # фактические результаты
```

Это схема расширения: пустые каталоги `src/tests/...` заранее не размножаются.
Новый раздел получает следующий свободный номер и ссылку из PLAN.md; подпункт —
следующий номер в разделе и ссылку из README раздела. Существующие ID не меняются.
Более глубокая самостоятельная часть получает README и ссылку из родительского
README; её цель, входы, результат и владелец должны быть понятны без чтения кода.

Одна функция имеет одно место исходников. Если её используют несколько разделов,
оставьте реализацию у ведущего владельца и добавьте ссылки, а не копии.
Статус хранится в карточке подпункта: `запланировано`, `готово к выполнению`,
`выполняется`, `проверяется`, `завершено` или `заблокировано`.
Готовность требует зависимостей и рассмотренной спецификации; завершение — проверки
критерия и рассмотрения вторым создателем. Частично выполненную задачу не закрывать.

## Общие файлы и сборка

[Контракты](contracts/README.md) имеют одну авторитетную версию. На изменение
назначается один автор задачи, оба рассматривают результат. Если контракта нет,
потребитель сначала готовит предложение, затем ожидает согласованную версию.

Корневые инструкции, общие документы и сборочный manifest также изменяет один
назначенный автор задачи. Параллельные исполнители согласуют эти изменения сообщением,
не перезаписывают общий файл друг за другом.

Исходники сохраняются в библиотеке автора; [интеграция](INTEGRATION.md) создаёт
отдельный аддон по согласованному manifest. Создаваемые файлы не становятся вторыми
редактируемыми копиями. Игровая установка изменяется только отдельным действием.

## Первая работа и границы результата

Первый выполняемый подпункт — [C1-01-01](../creator-1/01-foundation/01-environment-audit/README.md).
Он обследует среду без изменения Steam/Dota. Windows-путь пользователя:
`D:\AI\dota2coach`. Пока облачный Linux не подключён к этому компьютеру,
клонирование туда и запуск Workshop Tools не считаются выполненными.

Последующее уточнение: пользователь подтвердил существующий Windows-клон и выбрал
роль создателя 2. Активная задача — C2-01-foundation; [локальное продолжение](../creator-2/01-foundation/01-workspace-audit/notes/windows-start.md).
Подтверждение клона пользователем не означает нативный прогон из облачного Linux.

Следующая техническая сцена проверяет одного героя и синтетический ИИ. Аудит данных
и прав можно проводить параллельно независимо от её результата. Подтверждение
сходства с реальными игроками и настоящая речь проверяются отдельными вехами.

Основной исполнитель сам отвечает на вопросы и ведёт обсуждение. Критик подключается
только после завершения подпроекта; по умолчанию один, дополнительные — для конкретных
неразрешённых вопросов либо по запросу пользователя. Критик не заменяет второго владельца.
Назначение агентов и учёт регулируют [экономный порядок](AGENT-EFFICIENCY.md) и
[настройки](agent-policy.json).
